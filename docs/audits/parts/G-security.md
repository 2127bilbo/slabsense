# G. Security

**Summary.** Two Blockers let any signed-in user grant themselves unlimited credits from the browser (unrestricted `profiles` UPDATE policy; a world-open `credit_transactions` INSERT policy that feeds `refund_credits`). Six Majors: unauthenticated Stripe portal and checkout routes that trust a body `userId`, an unauthenticated Claude-vision route, user-editable grades that flow onto public slab certs, public user-photo bucket, body-selectable multi-provider fan-out, and no rate limiting anywhere; plus two secret exposures (TAG signing keys committed in two tracked files; Google + OpenAI keys in an untracked, un-ignored root file, both needing rotation). RLS is otherwise sound (select-own everywhere, slab/credit writes service-role only, SECURITY DEFINER RPCs revoked from anon/authenticated), the Stripe webhook verifies signatures and is idempotent, and no XSS sink was found (React has none; the 8 `innerHTML` sites in `public/slab/*.js` all go through `esc()`).

Severity: **Blocker** = exploitable today for money/credits or account data; **Major** = fix before submission; **Minor**/**Note** = Phase 3 if cheap / record.

## Findings

G-01 | **Blocker** | supabase/migrations/001_initial_schema.sql:25-26; columns added in 002_credits_system.sql:8-20 | Least privilege (RLS) | Policy `"Users can update own profile" FOR UPDATE USING (auth.uid() = id)` has no column restriction, and `profiles` carries `credits_balance`, `subscription_status`, `credits_expire_at`, `used_trial`, `signup_bonus_*`. From the browser console with the anon key and a normal session: `supabase.from('profiles').update({credits_balance: 9999, subscription_status: 'lifetime'}).eq('id', uid)` succeeds; `spend_credits` (20260915:81-110) then honours it. `src/services/auth.js:26` already does generic `.update(updates)`. | Drop the policy. Replace with either a `BEFORE UPDATE` trigger that raises when `auth.role() = 'authenticated'` and any billing column changes, or `WITH CHECK (credits_balance IS NOT DISTINCT FROM (select credits_balance from profiles where id = auth.uid()) AND …)` for every billing column, or move profile edits behind an API route. Also `REVOKE UPDATE (credits_balance, subscription_status, …) ON profiles FROM authenticated`. Verify in the dashboard, not just the file.

G-02 | **Blocker** | supabase/migrations/002_credits_system.sql:96-97; refund RPC 20260915_credits_atomic.sql:135-158; api/credits/refund.js | RLS / trust boundary | `CREATE POLICY "Service role can insert transactions" … FOR INSERT WITH CHECK (true)` applies to anon and authenticated (no `TO service_role`; the service role bypasses RLS anyway). The 20260915 migration drops only the select policy. Exploit: insert `{user_id: me, amount: -100000, transaction_type: 'grade_ai'}` with the anon key, then `POST /api/credits/refund {transactionId}` → `refund_credits` checks owner, type and `refunded_at` only, and credits `abs(amount)`. The legacy path (api/_lib/credits.js:160-185) is the same. | `DROP POLICY "Service role can insert transactions" ON credit_transactions;` (no user write policies at all). Cap refunds to the tier cost (`least(abs(v_tx.amount), <tier cost>)`) and require `v_tx.amount < 0` as defence in depth.

G-03 | Major | api/stripe/create-portal.js:35-61 | Authentication / IDOR | No `requireUser`; `userId` from body; returns a Stripe Billing Portal URL for any profile's `stripe_customer_id` (invoices, card last-4, billing address, cancel or change subscription). Called from src/services/credits.js:122. | `requireUser`, use `user.id`, ignore body `userId`; allow-list `returnUrl` to the app origin.

G-04 | Major | api/stripe/create-checkout.js:57-107,137-141 | Authentication / open redirect | For every non-slab price key the route is unauthenticated and trusts body `userId` (memory note confirmed): anyone can create Stripe customers for any profile id, enumerate ids (404 vs 400), spam checkout sessions, and set `successUrl`/`cancelUrl` to an attacker page the buyer lands on after paying. `quantity` for `single` is unbounded. | `requireUser` for all keys (the slab branch at 72-76 is the pattern); drop body `userId`; restrict `successUrl`/`cancelUrl` to `VITE_APP_URL`; clamp `quantity` 1–50. This route moves to Apple IAP for the native app (section B) but stays live for the web.
