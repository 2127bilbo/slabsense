# L. Account lifecycle

Read-only audit, 2026-10-01, on `tag-dataset` (same `src/`, `api/`, `supabase/` as `main`). Supabase email/password only; no native shell yet, so deep-link items are judged on what the web code would need.

**Summary:** 2 Blocker, 6 Major, 6 Minor, 6 Note (20 findings).
**Blockers:** "Delete Forever" deletes scans only — `profiles` has no DELETE policy, `auth.users` is never touched, storage/Stripe/credits/slabs are left, and the user can sign straight back in (L-01); the deletion call fails outright with a raw FK error for anyone who has ordered a slab (L-02).
**Biggest gaps after that:** no password reset, no email/password change, no resend-confirmation (L-03/L-04); privacy policy promises export and 30-day deletion that do not exist (L-05); Supabase dashboard auth settings (confirm-email, Site URL, redirect allow-list, Apple provider) are not recorded anywhere in the repo (L-06).

## Flow traces

### 1. Sign-up
- UI: `src/components/Auth/AuthModal.jsx:11-246`. Fields: Display Name (optional, `:120-143`), Email (`type=email required`, `:149-166`), Password (`required minLength=6`, `:173-191`). Validation is HTML-only; no confirm-password, no strength rule beyond Supabase's default 6.
- Call: `AuthModal.jsx:30` → `useAuth.signUp` (`src/hooks/useAuth.js:59-78`) → `supabase.auth.signUp({ email, password, options.data.display_name })`; `display_name` falls back to the email local part (`useAuth.js:69`). A duplicate implementation exists in `src/services/auth.js:10-27` (imported nowhere for sign-up).
- Profile row: DB trigger `handle_new_user` on `auth.users` insert (`supabase/migrations/001_initial_schema.sql:29-42`) inserts `profiles(id, display_name)`; credits/referral columns default via `002_credits_system.sql:8-20` / `20260915_credits_atomic.sql:17-26`.
- Email verification: the UI assumes it is ON — `AuthModal.jsx:31` always shows "Check your email to confirm your account!" and leaves the modal open. Nothing in the repo (no `supabase/config.toml`, no runbook) records the project's "Confirm email" setting, Site URL, or redirect allow-list; `.env.example` has only URL + anon key. If confirmations are OFF, `signUp` returns a session, `onAuthStateChange` (`useAuth.js:43-53`) signs the user in behind a modal that still says "check your email".
- Before verification: no session is issued; sign-in returns Supabase's "Email not confirmed" error verbatim (`AuthModal.jsx:37`). No "resend confirmation" control exists.
- Duplicates: with confirmations ON, Supabase returns a fake success (obfuscated user, no error) → the user sees "Check your email" and never learns the address is taken; with confirmations OFF, the raw "User already registered" message is shown. Either way the string comes straight from `err.message`.
- Terms: passive text "By creating an account, you agree to our Terms of Service and Privacy Policy." (`AuthModal.jsx:238-241`) with no links, no checkbox, nothing stored. The documents live only in `docs/TERMS_OF_SERVICE.md` and `docs/PRIVACY_POLICY.md`; no route serves them.

### 2. Sign-in and sessions
- `AuthModal.jsx:33` → `useAuth.signIn` (`useAuth.js:81-97`) → `signInWithPassword`. Errors shown verbatim (`AuthModal.jsx:37`).
- Client: `src/services/supabase.js:14-16` calls `createClient(url, anonKey)` with no options → supabase-js 2.101.1 (`package-lock.json:1371`) defaults: `persistSession: true` in `localStorage` under `sb-<project-ref>-auth-token` (access + refresh token, readable by any script on the origin), `autoRefreshToken: true` (timer refreshes ~1 h JWTs while the page is alive), `detectSessionInUrl: true`, `flowType: 'implicit'`.
- Expiry/refresh: no explicit handling; `useAuth.js:34-55` reads `getSession()` once and subscribes to `onAuthStateChange`. API calls send the JWT as Bearer (`src/services/credits.js:4,24`) and `api/_lib/auth.js:10-16` verifies it with `db.auth.getUser(token)`; a 401 on a paid grade re-opens the auth modal (`src/App.jsx:2359-2360`). In a WKWebView the refresh timer stops when the app is backgrounded; nothing calls `startAutoRefresh()`/`stopAutoRefresh()` on app-state changes.
- Sign-out paths: `UserMenu.jsx:183-205` → `useAuth.signOut` (`useAuth.js:100-112`, default `scope: 'global'`, so every device's refresh token is revoked); after Delete Account (`src/services/auth.js:158` then `ProfileSettings.jsx:62`); studio page `public/slab/studio.js:284`. If `supabase.auth.signOut()` throws (offline), local state is not cleared (`useAuth.js:104-111`).
- Multi-device: unlimited concurrent sessions (Supabase default); no session list or "sign out everywhere" UI beyond the implicit global sign-out. The studio page shares the same localStorage session on the same origin (`studio.js:265`, runbook `docs/superpowers/runbooks/slab-order-setup.md:56`).

### 3. Password reset, email change, password change
- None. `grep resetPasswordForEmail|updateUser|PASSWORD_RECOVERY` over `src/`, `api/`, `public/` returns nothing. `AuthModal.jsx` has no "Forgot password" link; `ProfileSettings.jsx:174-197` renders the email read-only; no password field anywhere.
- Deep links the native app must handle once these exist (and today for the confirmation link): Supabase sends `{SITE_URL}/#access_token=…&type=signup|recovery|email_change` (implicit) or `?code=…` (PKCE). With `flowType: 'implicit'` the token lands in a URL fragment that a custom-scheme/universal link must deliver to the WebView and `detectSessionInUrl` must see; PKCE (`flowType: 'pkce'` + `exchangeCodeForSession`) is the supported path for native. Redirect allow-list entries for the app scheme/universal link are a dashboard setting not recorded in the repo.

### 4. Guest use (what is gated)
- Not gated: capture, the free software grade, centering tool, card identification display, the disclaimer gate. `src/App.jsx` never checks auth before the local grade.
- Gated on sign-in: AI / Deep AI grades (`App.jsx:2327` opens `AuthModal`; server also requires a JWT, `api/_lib/auth.js:10`), Save to collection (`App.jsx:2104`), Collection tab (`App.jsx:3476-3481`, lock screen), credit balance (`App.jsx:2668`), slab order (needs a saved scan; `api/stripe/create-checkout.js:68-72` verifies the JWT for `priceKey === 'slab'`), identification logging (RLS `20260914_card_identifications.sql:19-20`).
- Free tier after sign-in: 5 saved cards (`api/credits/balance.js:65`), `canUseAI: false` for `subscription_status === 'free'` (`balance.js:80`).

### 5. Account deletion (full path)
- Button: `src/components/Settings/ProfileSettings.jsx:404-419` → confirm panel `:421-493` (type DELETE) → `handleDelete` `:55-68` → `deleteAccount(user.id)` in `src/services/auth.js:136-159` → `onSignOut()` → `onClose()`.
- `deleteAccount` runs **in the browser with the anon key** under RLS: (a) `DELETE FROM scans WHERE user_id = me` (`auth.js:142-147`); (b) `DELETE FROM profiles WHERE id = me` (`auth.js:150-155`); (c) `signOut()` (`auth.js:158`). No API route, no service role, no `auth.admin.deleteUser`. The comment at `auth.js:131-135` admits "the auth.users entry requires admin/service role … For now, we just delete user data".
- What the user is told: "This will permanently delete your account and all saved scans. This action cannot be undone." (`ProfileSettings.jsx:429`). Nothing about credits, subscriptions, open slab orders, or that the login survives.

- Guideline 5.1.1(v): "offer account deletion within the app… deletion of the entire account record, not just deactivation"; apps with subscriptions must tell users how to cancel. Today the flow is neither complete nor informative. Privacy policy (`docs/PRIVACY_POLICY.md:48`) promises "All associated data is permanently deleted within 30 days".

### 6. Referrals
- Schema only: `profiles.referral_code`, `referred_by` (`002_credits_system.sql:18-19`), `referrals` table (`:57-69`), `system_settings.referrals_enabled` (`:75-84`). Award path: `api/stripe/webhook.js:382-440` (`checkReferralBonus` after a paid checkout, +5 credits to the referrer, 30-day expiry reset).
- No code anywhere generates a code, shows it, or sets `referred_by`/inserts a `referrals` row (`grep referral_code|referred_by src api` → only the webhook read at `webhook.js:397`). The system is dormant; `docs/PAYMENT_PLAN.md:115-131` describes it as a plan. Abuse controls that exist on paper: paid-only qualification (`webhook.js:409`), global toggle. None for self-referral or alt emails since nothing writes rows.

### 7. Admin
- `ADMIN_USER_IDS` env → `adminIdsFromEnv` (`api/_lib/auth.js:18-20`) → `requireAdmin` (`:22-26`) guards `GET /api/slabs/queue` and `POST /api/slabs/status` (`api/_lib/routes/slabs-queue.js:13`, `slabs-status.js:12`).
- Admin UI: `public/studio.html` served at `/studio` and `/queue` (`vercel.json:24-31`), with its own email/password form (`studio.html:92`) using the same Supabase session (`public/slab/studio.js:265-285`). Not linked from the consumer React app (`grep studio src/` → none), but it is a public URL on the same origin: any signed-in user sees the Queue/Manual buttons and gets "Queue failed: forbidden" (`studio.js:230`). Manual mode (label rendering, "Signing secret" field `studio.html:269`) works for anyone.
- Legacy: `graded_references` write policy keys on `auth.jwt()->>'role' = 'admin'` (`20250108_create_graded_references.sql:68-69`), a claim nothing issues.

### 8. Data export
- None. `src/components/Export/ExportCard.jsx:1-4` is a share-image generator; `CollectionView.jsx` has delete/update only. Privacy policy promises "Access: Request a copy of your personal data" and "Export: Download your scan history" (`docs/PRIVACY_POLICY.md:72-75`).

### 9. Sign in with Apple
- Not required today (4.8 applies only when a third-party social login is offered; none is — `grep signInWithOAuth|signInWithIdToken src` → none). No `apple` provider reference in the repo; dashboard provider state unknown (L-06). If any social login is added: enable Apple in Supabase (Services ID, key, team id), call `signInWithIdToken({ provider: 'apple', token })` from the native ASAuthorization flow, register the redirect, and handle Apple's relay email in `handle_new_user` (`001:33` uses `split_part(email,'@',1)` as display name — fine, just ugly).

### 10. Disclaimer gate and terms acceptance
- Gate: `src/App.jsx:1526-1529` shows the modal unless `localStorage.slabsense_disclaimer_acknowledged` is set; "I Understand" writes `'true'` (`App.jsx:2641`). Per-device, unversioned, never stored server-side, not tied to the account, lost on clear-site-data. Not a terms acceptance — it is the "not affiliated / estimates only" notice.
- Terms acceptance: not stored, not versioned (see §1). TOS "Changes" (`TERMS_OF_SERVICE.md:220-222`) relies on "continued use".
